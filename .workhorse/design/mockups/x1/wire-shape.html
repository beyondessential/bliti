Capabilities Proposed

Three members, each saying something different: document is what a document may carry, radio is what the hardware is, acts is what the device will do on request.

One rule for document: it mirrors the configuration document

at a member of the document, capabilities carrymeaning
nothingNot supported. A document carrying it is invalid, and the client does not offer it (NET, NSCR).
trueSupported, with any value the document itself admits.
an arraySupported, with exactly these values.
an objectSupported, and constrained member by member, recursively. For a member whose values depend on another (a channel on a band), keyed by that other member's value.

Attachment and security kinds are keys, so a kind absent from capabilities cannot be proposed. A kind present supports its required members (label, ssid, passphrase); only its optional members and its constrained values are listed.

Because the rule is generic, one checker in bliti-core can serve both ends: the device rejects with it, and the client's pre-proposal check of NSCR is the same code through wasm. The at it reports is the Normalized Path of the first member not covered.

radio: facts HOT requires to be reported

membervaluesmeaning
alongsideindependent
shared-channel
one-at-a-time		How the radio runs a hotspot beside a wireless client. Written whenever radio is. shared-channel is why band, channel and channel-width are absent, and is the sentence the client shows in their place. one-at-a-time makes a document with both a hotspot and a wireless candidate invalid.

No radio at all means no wireless hardware, and then document carries neither wireless nor hotspot.

acts: keyed by message type

scan and survey are true where offered; wps is the array of methods the radio offers (WLAN). CFG already requires survey to be absent where the radio cannot survey.

Channels follow the country in force

Channel lists are those usable under the regulatory domain the device is running. A proposal that changes the country changes what is usable; see the open question below.

Vocabularies the specs leave open Proposed

wherevaluesnotes
invalid.reached carrier, association, addressing, gateway The stage the attempt stopped at. Everything before it passed. Wired candidates have no association. Absent only for a fault found before anything was applied, so a failure at carrier is still told apart from one.
invalid.at RFC 9535 Normalized Path $['attachments'][1]['gateway'], $['hotspot']['share-upstream']. The normalized form is the one spelling of a node, so the client finds the field by comparing strings; the dot shorthand cannot carry a hyphenated name. Rooted at the document for a proposal, and at the act's own message for an act: $ for a survey the radio cannot do, $['method'] for a WPS method it does not offer.
band 2.4ghz, 5ghz, 6ghz Shared with the band member of NFO's channel trait, so the value an operator sets reads the same as the one reported.
channel-width 20, 40, 80, 160 Megahertz.
dhcp-range a subnet, "10.41.0.0/24" The device takes the first host and hands out the rest. One subnet rather than a start and an end, because the device needs a subnet for itself anyway and a range outside it is meaningless. The fixed default is chosen with the renderer.
enterprise security eap, identity, anonymous-identity, password, phase2, ca-certificate, domain, client-certificate, client-key, client-key-passphrase Certificates and keys inline as PEM. ca-certificate is required, and domain where the method allows it: without them the access point is not authenticated, which WLAN forbids joining. phase2 is required for PEAP and TTLS, and members a method does not use are refused.

Gaps the specs need closing Open

1. Candidate state has no message

NSCR requires each candidate's state beside it: default route, up, and each way it is unavailable, described by what the device observed. The design shows "No gateway", "No lease", "Out of range". No CFG message carries any of it. Proposal: a device-sent state on the session stream, after the first configuration and whenever it changes, positionally matching the attachments of the configuration running now (a proposal once one is applied).

{
  "type": "state",
  "attachments": [
    { "is": "default-route" },
    { "is": "unavailable", "reached": "gateway", "reason": "192.168.60.1 did not answer" },
    { "is": "standby" }
  ]
}

is is default-route, up, standby (not tried, because a candidate above it holds the same interface) or unavailable. An unavailable candidate reuses reached and reason from invalid, so "No lease" is reached: addressing and "Out of range" is reached: carrier on a wireless candidate. The client words each; the device only names the stage.

2. What wps is answered with

CFG answers scan and survey, but says nothing of wps. Joining by WPS learns a credential, which is a change to the document. Proposal: the device answers with configuration carrying the document with the joined network added first, then applied or invalid. From there it is an ordinary proposal: confirm keeps it, discard or leaving forgets it, and the learned passphrase is visible like every other secret (NET).

3. Capabilities that change with the country

CFG puts capabilities on the first configuration only, but applying a new regulatory-domain changes which channels are usable. Proposal: applied carries capabilities whenever the proposal changed them, and the client revalidates against the new set.

4. What a device runs before anything is confirmed

A device out of the box has no recorded configuration. {"attachments": []} attaches to nothing, not even the wall port, and once bliti owns the network outright, restoring it at boot takes down whatever the image brought up. Proposal: an unconfigured device records one wired-dynamic candidate per wired interface, labelled by the interface, and runs no hotspot, so a device plugged into a network with DHCP is reachable before anyone configures it.

5. SAE held to SAE

A candidate of kind sae should not quietly join a WPA2-only access point of the same name. Whether iwd can hold one network to SAE is being checked alongside the renderer. If it cannot, the device should verify the negotiated key management after association and fail the candidate at association, rather than drop sae from its capabilities.

6. WPS by PIN has nowhere to put the PIN

WLAN requires joining by PIN, but wps carries only method, and nothing comes back. As the joining party the device generates the PIN, and the operator types it into the access point. Proposal: the device answers wps by PIN with pin carrying the digits, before the configuration and applied of gap 2.

{ "type": "pin", "pin": "12345670" }

7. A proposal interrupted before it is answered

CFG is silent on a discard, or a new proposal, arriving while one is still being verified. Proposal, as built: every proposal gets exactly one answer, so an interrupted one is answered invalid at $ with no reached, and the client pairs answers with proposals by counting. discard itself is not answered.

8. A public resolver hides the site's own names

LINK queries a candidate's nameservers before the ones the network supplies, and its note says that lets an operator add a public resolver without losing the site's internal names. On resolved it does not: the next server is tried only when one errors, and a public resolver answering "no such name" has not errored. Proposal: the search domains a network supplies become routing domains for that link, so names under the site's domain always go to the site's resolvers, and configured resolvers answer everything else. This holds only where the site hands out its domain, which the note should then say.
