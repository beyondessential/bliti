Configuration session wire shape

What goes over a configuration session stream (CFG), including the parts the specs leave to the implementation. Settled: all of it is now in NET, CFG, LINK, WLAN, HOT and NSCR, which govern where this and they differ.

Capabilities Pinned

Three members, each saying something different: document is what a document may carry, radios is what the hardware is, acts is what the device will do on request.

One rule for document: it mirrors the configuration document

at a member of the document, capabilities carrymeaning
nothingNot supported. A document carrying it is invalid, and the client does not offer it (NET, NSCR).
trueSupported, with any value the document itself admits.
an arraySupported, with exactly these values.
an objectSupported, and constrained member by member, recursively.
an object keyed by the member's valuesWhere what its siblings may carry depends on this member's value, each key is a value it may take, holding the constraints on its siblings under that value. The attachment kind, the security kind, a radio's interface and a hotspot's band all work this way, each wrapping its keys under its own name, as "attachments": {"kind": {"wireless": …}}. A key with nothing further to constrain holds {}. Left unset, the member is allowed where any key allows what the rest of the document asks.

A kind present supports its required members (label, ssid, passphrase); only its optional members and its constrained values are listed. For enterprise that means only eap: the credentials each method uses come with the method (WLAN).

Because the rule is generic, one checker in bliti-core can serve both ends: the device rejects with it, and the client's pre-proposal check of NSCR is the same code through wasm. The at it reports is the Normalized Path of the first member not covered.

radios: what the hardware is, keyed by wireless interface

membervaluesmeaning
modeltextWhat the adapter is, so an operator can tell the built-in radio from a USB one without knowing interface names.
bands2ghz, 5ghz, 6ghzThe bands the radio can use at all. A new access point only helps the device on one of these.
alongsideindependent
shared-channel
one-at-a-time		How this radio runs a hotspot beside a wireless client (HOT). Written for every radio able to run an access point; a radio that cannot is absent from document.hotspot.interface. shared-channel is why that radio's band, channel and channel-width hold only while no wireless candidate could share the radio (HOT), and is the sentence the client shows in their place once one could.

No radios means no wireless hardware, and then document carries neither wireless nor hotspot. Where radios differ, what each can do sits under its key in document; a candidate or hotspot naming no interface is allowed where any radio allows it, and the device picks (LINK, HOT).

acts: keyed by message type

Each mirrors its message the way document mirrors the document, keyed by interface as each act may name one. Under scan and survey are the radios able to do each; under wps, the methods each radio offers (WLAN). An act naming no interface runs on every radio listed, or for wps on one the device chooses. Scanning takes a radio off its channel for a moment, so naming one spares the rest: the uplink, or the hotspot's clients.

Vocabularies Pinned

Settled and written into CFG, LINK, WLAN, HOT and NFO.

wherevaluesnotes
invalid.reached carrier, association, addressing, gateway The stage the attempt stopped at. Everything before it passed. Wired candidates have no association. Absent only for a fault found before anything was applied, so a failure at carrier is still told apart from one.
invalid.at RFC 9535 Normalized Path $['attachments'][1]['gateway'], $['hotspot']['share-upstream']. The normalized form is the one spelling of a node, so the client finds the field by comparing strings; the dot shorthand cannot carry a hyphenated name. Rooted at the document for a proposal, and at the act's own message for an act: $ for a survey the radio cannot do, $['method'] for a WPS method it does not offer.
band 2ghz, 5ghz, 6ghz Shared with the band member of NFO's channel trait, so the value an operator sets reads the same as the one reported.
channel-width 20, 40, 80, 160 Megahertz.
dhcp-range one subnet, "10.41.0.0/24" The device takes the first host and hands out the rest. Unset is 10.41.0.0/24. Settled and written into HOT.
enterprise security eap, identity, anonymous-identity, password, phase2, ca-certificate, domain, client-certificate, client-key, client-key-passphrase Certificates and keys inline as PEM. ca-certificate is required, and domain where the method allows it: without them the access point is not authenticated, which WLAN forbids joining. phase2 is required for PEAP and TTLS, and members a method does not use are refused.

networks, answering scan Pinned

One entry per access point the radio heard, rather than per network. A network is usually several access points, and a single physical access point often carries several BSSIDs, one per band and per SSID. Which one the device hears best is what decides both questions a scan answers:

  • Joining: which network to add, and whether the device hears it well enough to be worth adding.
  • Siting a new access point to improve the device's signal: how well it hears each existing one, and which channels are already taken where the device stands.

Grouping by SSID is left to the client, which is where it is drawn. The device knows no more about which access points form one network than the client does, and two unrelated networks can share a name.

membermeaning
interfaceThe wireless interface whose radio heard it. An access point heard by two adapters appears once for each, with each one's signal, which is how an operator finds which adapter hears the site better.
bssidThe access point's radio address, lower case and colon-separated. The one member that tells two access points of one network apart.
ssidThe network's name, or null where the access point hides it and the device does not know it. A hidden network the device is configured for carries its name.
hiddenWhether the access point leaves its name out of its beacons. Written every time, since a hidden network whose name the device knows would otherwise look like any other.
securityWhat the access point advertises, from psk, sae, enterprise, open, owe and wep. Per access point, because one misconfigured access point in a network is exactly what a technician needs to find. The device will not join the last three, and the client compares the rest with capabilities.document.attachments.wireless.security.
band, channel, channel-widthWhere it operates. The width says how much of the band it occupies, which is what siting a new access point beside it has to avoid.
signalHow strongly the device hears it, in dBm.

The answer is a fresh scan, not whatever the radio last cached. The device leaves its own hotspot out.

What the client makes of it Pinned

Networks are listed by SSID, each showing the strongest signal among its access points and how many there are, with the access points behind it on expanding. Access points with no SSID are left out unless the operator asks to see hidden networks. Picking one prefills a hidden candidate with its security, leaving the SSID to type.

Siting wants a second reading of the same answer: every access point by signal, and the channels taken on each band the radio can use. Whether the screen grows a view for it is a separate question, below.

Gaps closed in the specs Pinned

1. Candidate state has no message

NSCR requires each candidate's state beside it: default route, up, and each way it is unavailable, described by what the device observed. The design shows "No gateway", "No lease", "Out of range". No CFG message carries any of it. Proposal: a device-sent state on the session stream, after the first configuration and whenever it changes, positionally matching the attachments of the configuration running now (a proposal once one is applied).

{
  "type": "state",
  "attachments": [
    { "is": "default-route" },
    { "is": "unavailable", "reached": "gateway", "reason": "192.168.60.1 did not answer" },
    { "is": "standby" }
  ]
}

is is default-route, up, verifying, standby (not tried, because a candidate above it holds the same interface) or unavailable. An unavailable candidate reuses reached and reason from invalid, so "No lease" is reached: addressing and "Out of range" is reached: carrier on a wireless candidate. The client words each; the device only names the stage.

2. What wps is answered with

CFG answers scan and survey, but says nothing of wps. Joining by WPS learns a credential, which is a change to the document. Proposal: the device answers with configuration carrying the document with the joined network added first, then applied or invalid. From there it is an ordinary proposal: confirm keeps it, discard or leaving forgets it, and the learned passphrase is visible like every other secret (NET).

3. Capabilities that change with the country

CFG puts capabilities on the first configuration only, but applying a new regulatory-domain changes which channels are usable. Proposal: applied carries capabilities whenever the proposal changed them, and the client revalidates against the new set.

4. What a device runs before anything is confirmed

A device out of the box has no recorded configuration. {"attachments": []} attaches to nothing, not even the wall port, and once bliti owns the network outright, restoring it at boot takes down whatever the image brought up. Proposal: an unconfigured device records one wired-dynamic candidate per wired interface, labelled by the interface, and runs no hotspot, so a device plugged into a network with DHCP is reachable before anyone configures it.

5. SAE held to SAE

A candidate of kind sae should not quietly join a WPA2-only access point of the same name. Whether iwd can hold one network to SAE is being checked alongside the renderer. If it cannot, the device should verify the negotiated key management after association and fail the candidate at association, rather than drop sae from its capabilities.

6. WPS by PIN has nowhere to put the PIN

WLAN requires joining by PIN, but wps carries only method, and nothing comes back. As the joining party the device generates the PIN, and the operator types it into the access point. Proposal: the device answers wps by PIN with pin carrying the digits, before the configuration and applied of gap 2.

{ "type": "pin", "pin": "12345670" }

7. A proposal interrupted before it is answered

CFG is silent on a discard, or a new proposal, arriving while one is still being verified. Proposal, as built: every proposal gets exactly one answer, so an interrupted one is answered invalid at $ with no reached, and the client pairs answers with proposals by counting. discard itself is not answered.

8. A public resolver hides the site's own names

LINK queries a candidate's nameservers before the ones the network supplies, and its note says that lets an operator add a public resolver without losing the site's internal names. On resolved it does not: the next server is tried only when one errors, and a public resolver answering "no such name" has not errored. Proposal: the search domains a network supplies become routing domains for that link, so names under the site's domain always go to the site's resolvers, and configured resolvers answer everything else. This holds only where the site hands out its domain, which the note should then say.

9. A view for siting a new access point

The scan above carries what siting needs, but NSCR draws only the joining use. Proposal: a coverage view reached from the scan, listing access points by signal with their channels, and the channels taken on each band the radio can use, so a technician placing a new access point can see where the device's signal comes from and which channel to put it on.
