Measurements and traits

The wire carries one message per reading: a measurement type, a set of traits saying what it is about, and a value. There is no identifier, no grouping, no ordering and no nesting. A reading's identity, and so its series, is its measurement together with its traits object.

The screen is the client's and does not move. Each tile is produced by a rule that selects on measurement and traits and aggregates — shown in blue above the messages that feed it.

The header

Rule. Take the hostname, board and os facts. Render as a header, not as tiles: they say which device this is, not how it is doing.
{ "type": "fact", "at": 20308140, "fact": "hostname",
  "kind": "text", "value": "tamanu-iti" }

{ "type": "fact", "at": 20308140, "fact": "board",
  "kind": "text", "value": "Raspberry Pi 5 Model B Rev 1.0" }

A fact has no state and no history, so it carries neither. It names itself with fact; a reading names itself with measurement, and the two catalogues may overlap freely.

Address

Rule. Select fact = network-address. Headline the one whose interface carries route: default, plus the one whose interface carries an overlay. All of them behind the tap.
{ "type": "fact", "at": 20308140, "fact": "network-address",
  "traits": { "interface": { "name": "eth0", "route": "default" } },
  "kind": "ipv4", "value": "192.168.1.42" }

{ "type": "fact", "at": 20308140, "fact": "network-address",
  "traits": { "interface": { "name": "tailscale0", "overlay": "tailscale" } },
  "kind": "ipv4", "value": "100.101.102.103" }

Which address to headline was a device-side judgement under the old shape. Here the device states the facts that make it decidable and the client decides.

The address family needs no trait: kind already says what the value is. A client that has never heard of ipv4 shows the string verbatim, which is correct without recognising it.

Storage

Rule. Select measurement = filesystem-usage, group by traits.filesystem. Headline the worst state, then the highest value. One row per filesystem behind the tap.
{ "type": "reading", "at": 20308140, "measurement": "filesystem-usage",
  "traits": { "filesystem": { "mount": "/boot/firmware", "device": "mmcblk0p1" } },
  "state": "warn", "kind": "fraction", "value": 0.9412 }

{ "type": "reading", "at": 20308140, "measurement": "filesystem-usage",
  "traits": { "filesystem": { "mount": "/", "device": "nvme0n1p2" } },
  "state": "ok", "kind": "fraction", "value": 0.7803 }

{ "type": "reading", "at": 20308140, "measurement": "filesystem-usage",
  "traits": { "filesystem": { "mount": "/mnt/data", "device": "nvme0n1p3" } },
  "state": "ok", "kind": "fraction", "value": 0.3129 }

Each filesystem carries its own state, so the device says which one is in trouble rather than leaving the client to infer it by comparing numbers. The old disk headline with filesystems in detail could not say it at all.

Network

Rule. Select measurement = network-throughput. Headline: sum every reading, both directions. Behind the tap: group by traits.interface, pair on traits.direction, draw each pair mirrored.
{ "type": "reading", "at": 20308140, "measurement": "network-throughput",
  "traits": { "interface": "eth0", "direction": "in" },
  "state": "ok", "kind": "quantity", "unit": "B/s", "value": 1200000 }

{ "type": "reading", "at": 20308140, "measurement": "network-throughput",
  "traits": { "interface": "eth0", "direction": "out" },
  "state": "ok", "kind": "quantity", "unit": "B/s", "value": 340000 }

{ "type": "reading", "at": 20308140, "measurement": "network-throughput",
  "traits": { "interface": "wlan0", "direction": "out" },
  "state": "fault",
  "error": "no counters while the interface is associating" }

The failed direction is a reading like any other, so it carries its own error and the reveal shows the reason. Under the old shape the mirrored pair rendered instead of the per-reading reveal, and a failed direction never showed why.

Memory

Rule. Select measurement = memory-usage for the headline and the bar. Select measurement = memory-bytes, group by traits.part, for the figures behind it.
{ "type": "reading", "at": 20308140, "measurement": "memory-usage",
  "state": "ok", "kind": "fraction", "value": 0.6154 }

{ "type": "reading", "at": 20308140, "measurement": "memory-bytes",
  "traits": { "part": "used" },
  "state": "ok", "kind": "quantity", "unit": "B", "value": 5153960756 }

{ "type": "fact", "at": 20308140, "fact": "memory-bytes",
  "traits": { "part": "total" },
  "kind": "quantity", "unit": "B", "value": 8375186227 }

Total is a fact and used is a reading, which is why the screen draws a sparkline under one and not the other. Nothing had to carry a graph flag to say so: the type says it.

This is also the catalogues overlapping — memory-bytes names both, and they are different things.

An unknown reading

Rule. No rule matched. Title-case the measurement for the label, render the trait values as the qualifier, draw the value by its kind. State still colours it, and it still gets a history. Append after everything recognised.
{ "type": "reading", "at": 20308140, "measurement": "modem-signal",
  "traits": { "modem": { "name": "cdc-wdm0", "technology": "lte" } },
  "state": "ok", "kind": "quantity", "unit": "dBm", "value": -71 }

{ "type": "reading", "at": 20308140, "measurement": "modem-signal",
  "traits": { "modem": { "name": "cdc-wdm1", "technology": "nr5g" } },
  "state": "ok", "kind": "quantity", "unit": "dBm", "value": -84 }

The traits have to be rendered, not merely ignored. Two modems share a measurement and differ only in the one trait the client cannot read. Dropping them would put two tiles on screen labelled "Modem signal" with different numbers and nothing to tell them apart.

Identity still works for the same reason: it is the traits object wholesale, so the two stay two series rather than collapsing into one garbled graph. That is what the container buys over reserving base names.

An unknown fact

Rule. As above, from fact rather than measurement, and without the parts a fact does not have: no state to colour by, no scale, no history. Label, qualifier and value.
{ "type": "fact", "at": 20308140, "fact": "firmware",
  "traits": { "component": "bootloader" },
  "kind": "text", "value": "2026-04-17" }

{ "type": "fact", "at": 20308140, "fact": "firmware",
  "traits": { "component": "eeprom" },
  "kind": "text", "value": "2026-02-03" }

An unknown fact is a tile, not a header entry. The header is the three facts this client knows name the device; anything else is something it has learned about the device and has nowhere better to put.
