One screen, three wires

The screen on the left is the client's, and it does not move. The client decides what it shows, in what order, under what labels, and it shows the same thing whichever shape the device sends. The only variable here is what the wire carries.

So the question is not which option looks better. It is which option carries enough for the client to draw the screen it has already decided on. Where an option cannot, the shortfall is marked in red in the message.

What all three agree on

One message type carrying a timestamp and readings. No group, no meaningful order, values rounded to four places. Network nests in every option, because an interface's in and out are two facts about one interface.

Exposed by writing it out: eth0 has no measurement of its own, only children. Today a reading must carry a value or an error. Either that rule relaxes to let children stand in, or a parent carries the aggregate of its children, as shown here. Worth settling either way.

Where they part company: Storage

The screen colours /boot/firmware amber and draws a bar per filesystem. That needs a state and a scale per filesystem.

1 · detail becomes readings

Every sub-value is a reading. One mechanism, nothing inert.

{ "name": "disk", "label": "Disk", "state": "warn", "graph": false,
  "value": { "kind": "fraction", "number": 0.9412 },
  "readings": [
    { "name": "boot-firmware", "label": "/boot/firmware",
      "state": "warn", "graph": false,
      "value": { "kind": "fraction", "number": 0.9412 } },
    { "name": "root", "label": "/", "state": "ok", "graph": false,
      "value": { "kind": "fraction", "number": 0.7803 } },
    { "name": "mnt-data", "label": "/mnt/data", "state": "ok", "graph": false,
      "value": { "kind": "fraction", "number": 0.3129 } }
  ] }

Draws the screen. Each filesystem has its own state and its own fraction, so the amber and the three bars come straight off the wire.

2 · readings alongside detail

A sub-fact that stands on its own nests; a figure that only qualifies its parent stays in detail. A filesystem stands on its own.

{ "name": "disk", "label": "Disk", "state": "warn", "graph": false,
  "value": { "kind": "fraction", "number": 0.9412 },
  "readings": [
    { "name": "boot-firmware", "label": "/boot/firmware",
      "state": "warn", "graph": false,
      "value": { "kind": "fraction", "number": 0.9412 } },
    { "name": "root", "label": "/", "state": "ok", "graph": false,
      "value": { "kind": "fraction", "number": 0.7803 } },
    { "name": "mnt-data", "label": "/mnt/data", "state": "ok", "graph": false,
      "value": { "kind": "fraction", "number": 0.3129 } }
  ] }

Draws the screen, identically to option 1 here. The two options only diverge on Memory, below.

3 · nesting only where it is a fact

Only an interface's in and out nest. Everything else stays in detail, as today.

{ "name": "disk", "label": "Disk", "state": "warn", "graph": false,
  "value": { "kind": "fraction", "number": 0.9412 },
  "detail": [
    { "label": "/boot/firmware", "value": { "kind": "fraction", "number": 0.9412 } },
    { "label": "/",             "value": { "kind": "fraction", "number": 0.7803 } },
    { "label": "/mnt/data",     "value": { "kind": "fraction", "number": 0.3129 } }
  ] }
no state per filesystem — the amber cannot be drawn
no name per filesystem — nothing to key a history to

Cannot draw the screen. The device knows /boot/firmware is the one in trouble and has no way to say so. The client can infer it by comparing fractions, which is the client guessing at a judgement the device already made.

Where 1 and 2 part company: Memory

The screen draws a sparkline under Used and none under Total.

1 · detail becomes readings

{ "name": "memory", "label": "Memory", "state": "ok", "graph": true,
  "value": { "kind": "fraction", "number": 0.6154 },
  "readings": [
    { "name": "used", "label": "Used", "state": "ok", "graph": true,
      "value": { "kind": "quantity", "number": 4.8, "unit": "GB" } },
    { "name": "total", "label": "Total", "state": "ok", "graph": false,
      "value": { "kind": "quantity", "number": 7.8, "unit": "GB" } }
  ] }

Draws the screen. used says its history is worth drawing and total says it is not, so the device makes the call rather than the client assuming.

2 and 3 · memory stays in detail

{ "name": "memory", "label": "Memory", "state": "ok", "graph": true,
  "value": { "kind": "fraction", "number": 0.6154 },
  "detail": [
    { "label": "Used",  "value": { "kind": "quantity", "number": 4.8, "unit": "GB" } },
    { "label": "Total", "value": { "kind": "quantity", "number": 7.8, "unit": "GB" } }
  ] }
no name, no graph flag — neither figure can carry a history

Cannot draw the sparkline under Used. The figure is on the wire every second and is structurally inert, which is the same defect the card already names for per-interface throughput.
